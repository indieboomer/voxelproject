## Start here

The World API lets Lua modules change the shared game world. You can describe
an outcome in ordinary language and have the local model generate Lua, or
write a module yourself. A rule changes what happens over time; an instant
spell performs an action when run. You do not need to learn every method to
start: choose a concrete outcome, review the generated behavior, and test it.

1. Open the Rule Console with the backquote/tilde key, describe your request,
   and submit it with Enter. State whether it should happen once or repeatedly.
2. Read the interpretation and any generation/validation feedback. Unsupported
   requirements should be clarified rather than silently replaced with a smaller effect.
3. In the Rules panel, use **View Code** to inspect the result. Generated modules
   are not automatically active.
4. The host clicks **Enable** for a continuing rule or **Run** for an instant
   spell. **Disable** stops future rule callbacks; **Delete** removes the module.
5. Test the trigger, the effect, and what happens when the condition ends.
   Save with **F5** when you want to retain the world and its modules.

The host controls activation and the authoritative world. When the host enables
guest prompting, a guest with local generation available can submit a proposal.
The host still reviews and activates it. A guest-requested instant, run by the
host, uses the requesting guest as caster and requires that guest to be connected.
Receiving a proposal does not execute it.

Normally a successfully created rule costs 20 mana once, with no upkeep, and a
successful instant cast costs 5 mana. The engine handles these fees; generated
Lua must not charge them again. Failed casts refund the reserved cast fee.
Host mana-free testing changes the effective fees to zero. Read
`api.rule_mana_cost` and `api.instant_mana_cost` rather than assuming fixed costs.
Custom material or mana costs requested as part of a rule are separate.

## Write prompts that produce useful rules

Describe **who or what**, **the trigger**, **the action**, **the area or amount**,
and **how the effect ends**. Use the game's material and equipment names when
you know them. The reference below lists every supported block and creature ID.

| Request | What to specify |
| --- | --- |
| One-time construction | Shape, dimensions, material, location and which existing blocks may change |
| Conditional creature behavior | Species, target species/players, condition and behavior afterward |
| A shrine or switch | Trigger block, interaction, target, cost and cooldown if wanted |
| A reward | Event, recipient, resource/item and amount |
| Weather-sensitive terrain | Material, radius, whether roofs protect it, and whether the change is permanent |
| A production machine | Device, recipe, inputs, power source and output destination |

Examples:

- "Build a five-by-five stone platform under me, filling only empty space."
- "At night wolves hunt chickens; during the day they wander peacefully."
- "Rain turns exposed soil within two blocks of players into mud; roofs protect it."
- "Interacting with a crystal heals sheep within six blocks and spends one life element."
- "Give the player who mines iron ore one additional coal."
- "Set the time to dawn once."

Distinguish protecting players from pacifying a species: preventing sheep from
hurting players need not prevent sheep fighting other creatures. Distinguish
following from attacking, owning a tool from equipping it, and granting resources
from crafting them using owned ingredients. A persistent instruction should say
whether to restore the old behavior when its condition ends.

One cast cannot modify an unlimited area. Keep instant construction within
300 changed blocks, or explicitly request gradual construction in small batches.
Avoid prompts that require arbitrary new native materials, models, general
physics changes or undocumented callbacks; those capabilities are not exposed.

## Choose callbacks and understand events

Every module defines exactly one primary callback: `on_tick` or `on_cast`.
Either module type may also define the three optional event callbacks.

| Callback | When it runs | Event data |
| --- | --- | --- |
| `on_tick(api)` | About ten times per second while a rule is enabled | No event argument |
| `on_cast(api, event)` | Once per host Run action | `player_id` only |
| `on_death(api, event)` | Creature death | `kind, x, y, z`; no killer ID |
| `on_block_break(api, event)` | A player mines a block | `kind, x, y, z, player_id` |
| `on_interact(api, event)` | A player presses F while aiming at a block | `kind, x, y, z, player_id` |

For an event-only rule, define an empty `on_tick` and implement the relevant
event callback. There is no built-in `on_jump`, `on_rain`, `on_enter_region`,
general `on_damage`, or chat callback. Use current snapshots and remembered
previous values in `on_tick` to detect transitions where appropriate. That
remembered Lua state is temporary and resets when the module VM reloads.

Scripted block edits do not trigger player mining/interaction events, and
interaction alone does not destroy or consume anything. Death handlers cannot
recursively generate an unlimited chain of death callbacks in the same tick.
Events may wait in bounded queues and query current world state when dispatched.

## Essential Lua conventions

All methods live directly under `api`: use `api.get_player(id)`, not
`api.player.get(id)` or `api:get_player(id)`. Properties such as `api.is_night`
are values, not functions. Call functions with parentheses.

```lua
function on_cast(api, event)
    local p = api.get_player(event.player_id)
    if not p then return end
    api.broadcast("Caster position: " .. p.x .. ", " .. p.y .. ", " .. p.z)
end
```

Player IDs are not array indexes. Player and creature IDs are separate
identities, even when their numbers happen to match. Position fields are
`x, y, z`, not a nested `position` table. Block coordinates are integers;
use `math.floor` on player coordinates, particularly at negative positions.
Player positions refer to feet.

Query results are detached snapshots. Modifying a returned table does not
change the world. After an action, query again if you need the updated state.
Queries within the callback see accepted staged writes from that callback.

Check documented results: methods can return `nil`, `false`, an empty list,
or a number. Lua treats zero as true. For shape edits, zero is a successful
no-op and `nil` is rejection. Older methods have different failure conventions;
the complete reference describes each one. Unknown `find_creatures` kinds
retain the legacy behavior of matching any creature, while unknown block
filters match nothing. Do not use misspelled IDs to mean "any".

Use `ipairs` for returned lists and `pairs` for maps such as inventory resources.
The available standard libraries are `table`, `string`, and `math`, along with
the sandbox's basic Lua functions. Files, networking, processes, imports and
engine memory are not accessible. Keep Lua short and use the documented helpers.

## Capabilities by task

### Players, movement and progression

Use `players`, `get_player` and `nearest_player` for position, movement, health
and environmental context. `nearest_player` takes three coordinates, never an
ID. Guest movement flags are approximated from network state.

`damage_player`, `heal_player`, `set_poisoned`, `set_player_speed`,
`set_player_jump` and `teleport_player` apply player effects. Movement
multipliers are bounded. Teleport bypasses collision and clears velocity;
the caller must choose a suitable destination. These are explicit actions,
not declarations that automatically undo themselves when a condition ends.

`get_player_journal` reports built-in progress, recovery location, quests and
recipe-book discovery. It is read-only: editing its table does not claim a
quest or reward. Peaceful quest-giver NPCs are separate from combat creatures.

### Inventory, equipment, elements and mana

`get_player_inventory` returns four parts: `resources`, `items`, `elements`
and `mana`. Resource keys are block/resource IDs; equipment keys are the
available tool/charm IDs. Element keys are `earth`, `fire`, `water`, `life`,
and `death`. Read counts with `get_resource_count`, `get_item_count`,
`get_element_count` and `get_mana`; use `has_resource` or `has_item` for checks.
The older `get_inventory` is resource-only.

Use `give_item`, `take_item`, `give_element`, `take_element`, `give_mana` and
`take_mana` for explicitly requested rewards or costs. Grants bypass crafting
costs. For actual crafting, use `craft_item`, `decompose_item`,
`decompose_resource` and `convert_elements_to_mana`, which use the host economy.
Inspect `get_item_recipe` and `get_resource_elements` instead of inventing costs.
Specialist equipment may require a discovered recipe book.

Ownership and selection differ: `get_equipped_item` reports the selected
right-hand resource/tool. Torches use a separate left-hand slot and do not
replace that selection. Crystals are ordinary resources and do not light the
world when held. The legacy `carrying_crystal` flag is not a substitute for
an actual inventory or equipment query. Granting an item does not automatically
equip it.

### Creatures, combat and protection

Inspect creatures with `creatures`, `get_creature`, `find_creatures` and
`nearest_creature`. Spawn with `spawn_creature` or
`spawn_creature_near_player`; fish have dedicated habitat-aware helpers.
Check returned IDs because creature counts, spawn budgets and habitat rules
can prevent spawning. Dragons have additional placement constraints.

Target selection and action are separate:

1. Choose a target with `set_target` or `select_target`.
2. Use `chase_target` to follow without damage, or `attack` to pursue and fight.
3. Use `ignore` to cancel pursuit and aggression, or `set_aggressive` to
   restore automatic hostile/peaceful behavior.

`chase` steers toward coordinates and needs refreshing. `get_behavior` reports
intent, not proof a hit landed. Combat damage and cooldowns remain species-specific.
Do not emulate ordinary melee by calling `damage` every tick. Direct `damage`,
`destroy`/`die`, and `heal_creature` are available for explicit magical effects;
healing caps at species maximum and cannot resurrect dead creatures.

For temporary restrictions, `protect_player` prevents a specified creature
attacking one player and `suppress_creature_attacks` prevents that creature
attacking any target. These are rule-owned policies: refresh them only while
the condition holds. They expire without permanently changing behavior settings.
Ordinary behavior overrides persist until explicitly changed, including saves.
Initial player protection can suppress creature attacks even when a rule
assigns an explicit target; direct scripted player damage is a separate action.

### Blocks, materials and construction

`get_block` reads a cell; `get_block_kinds` lists the material catalog and
`get_block_info` reports properties such as solidity, hardness and emission.
Metadata is read-only. Use `block_matches` and `find_blocks` for exact IDs or
the categories `any`, `wood`, `ore`, `leaves`, `plant`, `solid`, and `liquid`.
`ore` includes coal; `liquid` currently means water. Search results are bounded
and are not necessarily sorted nearest-first.

`replace_block` edits one cell. `fill_box` and `fill_sphere` create, excavate,
or transform groups of cells. The new `kind` is the material to place;
optional `filter` selects existing material. For example `kind="air"`
excavates, while `filter="air"` builds only in empty space.

Boxes include both corners and normalize their order. Spheres use an integer
center and coordinate-distance radius. Shape edits require loaded cells,
protect bedrock and occupied device cells, and reject the entire call if it
cannot complete within the remaining edit allowance. They cannot place bedrock.
All block-edit methods share the callback allowance; helpers do not grant
extra changes. No-op shape cells consume no edits. These world-edit powers
do not automatically pay materials or grant mining drops.

Use `is_block_loaded` because `get_block` also returns `air` for unloaded
terrain. `terrain_height` is procedural elevation. `surface_height` scans
actual loaded terrain and includes roofs, trees, devices and staged edits.
Neither is a query for the cave floor immediately below a player.

### Weather, daylight, shelter, campfires and water

Read `weather`, `is_raining`, `is_night` and `time_of_day`. Current weather
names are `sunny`, `rain`, `mist`, `storm`, and `windy`; rain and storm produce
rainfall. Time runs from sunrise at 0 through noon at 0.25, sunset at 0.5,
and midnight at 0.75. `set_weather`, `start_rain`, `stop_rain`,
`set_time_of_day`, `set_time_dawn` and `set_time_night` change those values.
Do not repeatedly reset time or restart the weather timer unless requested.

`is_exposed_to_sky` checks rain-blocking cells at or above a loaded position;
query one cell above a surface. It returns `nil` when terrain is unknown,
not proof of shelter. Leaves block rain; water does not. This is an exposure
test, not a numeric light-intensity query.

Place a campfire using `place_campfire` or `place_campfire_near_player`.
The latter searches suitable nearby terrain. `get_campfire` and
`find_campfires` report burning/light state. `get_water` reports depth,
surface and visual current; `get_waterfalls` reports eligible spills.
`can_spawn_fish` and `spawn_fish` require real water and clearance. Editing
water or obstructions can change those environmental effects; there is no
general fluid simulation or direct writable current/light-source override.

### Machines, storage and production

`get_devices` and `get_device` inspect automation. `place_device` builds a
device using a connected player's resources; it checks reach and full-height
clearance. `configure_device` changes supported settings and
`set_device_enabled` starts/stops its operation. Device snapshots are copies.
Occupied device cells cannot be replaced as ordinary terrain; use player
packing controls to preserve their contents.

Device matter maps use typed keys such as `resource:stone`, `item:pickaxe`,
`element:earth`, and `creature:sheep`. Inspect current recipes/configuration
and check action results. Production runs on host simulation ticks, without
an LLM call each cycle. Do not imitate crafting or smelting with free grants.
Disabling a device also stops transfers; for stock limits prefer the existing
sensor/valve arrangement. Paid batches keep their recipe until completion.

Smelters process supported ores into their corresponding metals using mana
or fuel. Feeding chests can eject contents or retain them for transfers;
`eject_contents=false` selects retention. `configure_device` documents all
supported settings in the full reference below; undocumented table keys are
not a way to create new machine capabilities.

### Notifications and diagnostics

Use `broadcast` for a player-visible message. Keep messages short and emit
them on meaningful transitions rather than every tick. Broadcasts share a
per-callback count and byte limit and roll back if the callback fails.

Chat and notification history is exported when the host saves as
`saves/<worldname>_chat.log`, including lines no longer visible in the on-screen
log. The transcript survives reload and repeated saves do not duplicate it.
This is the game's save feature, not Lua filesystem access or a chat event API.

## Complete Lua examples

These three examples are embedded from the executable example modules used
by the sandbox regression checks. Each code block is a separate module.

### One-time platform construction

Request: "Build a five-by-five stone platform under me, only filling air."

```lua
-- api_version: 1.33.0
-- Prompt: Build a five-by-five stone platform under me, only filling air.
function on_cast(api, event)
    local p = api.get_player(event.player_id)
    if not p then return end
    local x, y, z = math.floor(p.x), math.floor(p.y) - 1, math.floor(p.z)
    local changed = api.fill_box(x - 2, y, z - 2, x + 2, y, z + 2, "stone", "air")
    if changed == nil then
        api.broadcast("Cannot build here: check loaded ground and the edit limit.")
    else
        api.broadcast("Platform: placed " .. changed .. " stone blocks.")
    end
end
```

### Weather-sensitive ground

Request: "Rain turns exposed soil near players into mud, but roofs protect it."
This example makes permanent terrain changes and limits work to four accepted
changes per callback. It does not turn mud back into soil when the rain ends.

```lua
-- api_version: 1.33.0
-- Prompt: Rain turns exposed soil near players into mud, but roofs protect it.
function on_tick(api)
    if not api.is_raining then return end
    local changed = 0
    for _, p in ipairs(api.players()) do
        local cells = api.find_blocks("soil", math.floor(p.x), math.floor(p.y), math.floor(p.z), 2)
        for _, b in ipairs(cells) do
            if changed >= 4 then return end
            if api.is_exposed_to_sky(b.x, b.y + 1, b.z) == true then
                if api.replace_block(b.x, b.y, b.z, "mud") then changed = changed + 1 end
            end
        end
    end
end
```

### A resource-powered interaction shrine

Request: "Interacting with crystal heals nearby sheep, spending one life element."
The no-op `on_tick` makes this a rule; the interaction callback performs its action.
It only spends the element when an injured sheep is present.

```lua
-- api_version: 1.33.0
-- Prompt: Interacting with crystal heals nearby sheep, spending one life element.
function on_tick(api) end

function on_interact(api, event)
    if event.kind ~= "crystal" then return end
    local sheep = api.find_creatures("sheep", event.x, event.y, event.z, 6)
    local injured = false
    for _, c in ipairs(sheep) do
        if c.health < c.max_health then injured = true end
    end
    if not injured then return end
    if not api.take_element(event.player_id, "life", 1) then
        api.broadcast("The shrine needs one life element.")
        return
    end
    for _, c in ipairs(sheep) do
        if c.health < c.max_health then api.heal_creature(c.id, 4) end
    end
end
```

## Transactions, stopping rules and saving

Every callback stages effects and commits them only after successful execution
and budget checks. A callback error discards its staged terrain, inventory,
creature, weather/time, notification and player changes. It does not undo
earlier successful callbacks or the event that triggered it.

An ordinary action rejection (`false`/`nil`) does not automatically fail the
callback. If a structure or purchase involves several operations that must
succeed together, check every result and raise `error("Cannot complete action")`
on failure. A shape's rejection guarantees that shape staged nothing; earlier
successful calls in the callback still need explicit failure for rollback.
Budget exhaustion cannot be swallowed with `pcall` or `xpcall`.

Disabling a rule stops future work; it is not world history undo. Block edits,
inventory changes and explicit creature behavior overrides already committed
remain. For temporary rules, define the condition's exit behavior. Rule-owned
attack protection policies are the exception designed to expire automatically.

Saves retain module names, prompts, source and enabled flags, along with normal
saved world/player/creature state. Lua global variables, timers and remembered
tables do not survive world reload or rebuilding a failed module VM. Do not
promise permanent custom counters using plain Lua variables.

Current named worlds are stored in `saves/world-<name>.bin`; the default world
uses `saves/world.bin`. The preceding save is retained as `.bin.bak`.
Guest inventories are persisted by the host, but guest transient vitals reset
on reconnect. See the complete persistence and replication details below for
the practical limits of multiplayer state and save compatibility.

## Troubleshooting and working within limits

| Symptom | Check or change |
| --- | --- |
| Nothing happens after generation | Review the result, then host Enable or Run; proposals are not automatic activation |
| Player lookup is nil | Use `get_player(event.player_id)`; the requesting guest may have disconnected |
| Wrong creature species is affected | Check the exact kind ID; legacy unknown creature filters mean any |
| Shape returns nil | Loaded cells, dimensions, Y bounds, protected cells, material/filter spelling and remaining edit allowance |
| Shape returns zero | The operation succeeded but no matching cells needed changing |
| A roofed cell is mistaken for exposed | Compare exposure to `true`; `nil` means unknown, and surfaces must be queried at y+1 |
| Creature follows but does not fight | Select a target and call `attack`, not just `chase_target`; entry protection and cooldowns still apply |
| A conditional effect remains after Disable | Ordinary effects persist; implement exit behavior or an explicit cleanup action |
| Progress stored in a Lua table disappeared | VM state is not saved; use built-in saved systems where applicable |
| Insufficient materials/mana | Inspect inventory and recipe, then check the action result; do not double-charge engine fees |
| Rule exceeds execution budget | Reduce scan radii, avoid nested broad scans, update fewer actors/cells per tick and throttle repeated work |
| Unknown API member/material | Use the exact signatures/IDs below; there are no nested api.world/api.player namespaces |

Rules receive 32 block edits and four creature spawns per callback; instant
casts receive 300 edits and 30 spawns. Methods share 512 API calls and 65,536
native-work units per callback, alongside time, instruction and memory limits.
Shape scans consider at most 4096 cells; other query radii and result caps are
method-specific. A radius request larger than the documented cap is not a way
to query the whole world. Scans become more expensive after many staged edits.

Use small searches, avoid repeatedly scanning every creature's neighborhood,
and handle full/no-match results. The full reference that follows includes
every current method, property, callback, returned field, vocabulary and limit.
Runtime creation of native block types, models, textures, arbitrary saved
components and unrestricted engine access remains unsupported.

## Sandbox / engine

- Runtime: Lua 5.4 via mlua
- Tick interval: 0.1s (~10/sec)
- Allowed stdlib: table, string, math
- Removed stdlib: os, io, require, debug, package (never exist in this sandbox)
- Memory limit: 8,388,608 bytes
- Time budget: 5ms per call (checked every 1000 instructions)
- Instruction limit: 100,000 per initialization/callback
- Source limit: 65,536 UTF-8 bytes

Source is limited to 65,536 UTF-8 bytes. Initialization and every callback each receive 100,000 Lua instructions and a 5ms wall-time budget. Hooks check every 1,000 instructions; API entry/exit and execution completion also check time. Limits reset for each invocation. Budget exhaustion cannot be caught or suppressed with pcall/xpcall; ordinary Lua errors remain catchable. Native operations are not forcibly interrupted, so the time budget is a cooperative limit, not a hard realtime deadline. Each host tick/cast dispatch admits at most 16 callbacks under shared ceilings of 400,000 instructions, 4,096 API calls, 262,144 native work units and 20ms cooperative time. Admission reserves the full per-callback allowance (plus initialization for a failed VM reload); unstarted work waits for a later dispatch without resetting or replaying the callback. Nearby campfire placement charges (2*ceil(radius)+1)^2 * 72 units times (1 + staged block edits), plus the ordinary snapshot cost; radius is 2..8. Other environment queries/actions charge 200 units times (1 + staged block edits); find_campfires charges twice its bounding cube times (1 + staged block edits). Creature snapshots also account for staged-block lookups for in_water. Shape edits charge their bounding volume (at most 4096 cells) times (1 + staged block edits), before scanning. surface_height and is_exposed_to_sky charge at most 128 cells with the same multiplier; material catalog queries charge their catalog size with that multiplier. Native work is limited to 65,536 units per callback: find_blocks charges its bounding cube candidates times (1 + staged block edits); other methods charge 1 + creature count + player count + staged player effects + staged block edits. find_blocks also checks time between scan rows. These units conservatively bound repeated scans, not CPU instructions or hard realtime.

Pending callbacks use round-robin recipient queues, FIFO within each rule. Tick requests coalesce to one pending tick per rule. Events retain their original recipient and payload, but query current world state when run. Disabling/deleting a rule cancels its queued work. Re-enabling a rule or adding a new rule never delivers old events to that new activation. Queues hold at most 512 callbacks total and 64 per module; newest excess requests are dropped with a visible saturation notice. Only the first 512 incoming block-break events and first 512 interactions per dispatch are considered. Queues are transient and are not saved on world exit. Up to 64 modules are loaded; saved overflow or invalid source is preserved without execution and reported to the host. Removing loaded modules and reloading the world can make room for preserved overflow modules.

Each module gets its own Lua VM: one module's globals/persistent state can never leak into another's. Initialization errors reject the module; an unhandled callback error or instruction/time/API-call/broadcast budget violation disables a continuous rule and notifies the host. An instant spell reports failure for that cast and can be run again. Lua memory allocations are capped at 8 MiB; ordinary Lua errors, including allocation errors, can be handled by pcall/xpcall. World effects are staged per callback and committed only after successful execution and final budget checks. Failed callbacks discard every staged effect. Before retrying a failed cast or reactivating a failed rule, its Lua VM is rebuilt from source; Lua globals reset because explicit persistent module state is not implemented yet.

## Callback transactions

Each callback is one transaction. Block edits, creature spawning/chasing/ damage/destruction, player effects, inventory changes, weather (including its RNG/timer), time, and broadcasts are staged. Queries read the callback's own accepted writes plus earlier successful callbacks in the same host dispatch. Returned query tables are snapshots; query again after an action. time_of_day/is_night/weather properties refresh after API calls. Movement and physics are not simulated during a callback; terrain_height remains the procedural generator height, not a scan of edited blocks. Failed callbacks emit no death events, broadcasts, replication effects, or spawn ID/RNG advances. Successful callbacks commit in scheduler order. Death events enqueue one level of notifications only after their cause commits. A failing death handler rolls back only its own changes, not the earlier death that triggered it. Ordinary errors caught by Lua do not abort the transaction; instruction/time/API/native-work/broadcast budget failures cannot be caught. This is callback failure rollback, not user-facing history/undo or atomic network delivery. Shared admission bounds callback work; native commit/apply and operating-system scheduling can overrun the cooperative wall-time target.

## Multiplayer authority

Every World API call executes ONLY on the host -- Lua does not run on joined clients at all (ScriptHost is host-only state). A module's effects (block edits, creature spawns/state, weather, time of day, broadcasts, item grants, player attributes, player teleports) reach clients purely through the replication channels below; there is no separate "multiplayer mode" a rule opts into. Only the host can activate, disable, delete or run a module. If guest prompting is enabled, guests generate locally and send proposals for host review; receipt never activates them. A host-run guest instant uses the connected requesting guest's player ID and mana account. Otherwise the caster is the host. Always resolve event.player_id through get_player rather than hardcoding it.

Replication channel per kind of effect:

- **block_edits**: Retried until acknowledged and deduplicated (ReliableMsg::BlockEdit), but NOT ordered. Reordered writes to the same block can leave a client stale; ordered/revisioned replication is pending.
- **creature_state**: Best-effort, ~20 Hz (UnreliableMsg::Snapshot) -- a dropped snapshot is superseded by the next; no guaranteed delivery, but self-healing within one snapshot interval.
- **weather_and_time_of_day**: Carried in the same best-effort Snapshot as creature state -- see creature_state.
- **broadcast_messages**: One reliable Notify message per api.broadcast call, the same path used for host system notifications (rule enabled/disabled, player joined, etc.).
- **item_grants**: The host owns inventories for all players. Guest give_item/take_item changes are sent through reliable targeted CraftState updates; the host applies its own changes locally.
- **player_attributes**: health, poisoned, speed_multiplier, jump_multiplier, and oxygen all ride the same best-effort Snapshot creature_state already uses (~20Hz, self-healing) -- broadcast to every connected player, not just the one they belong to, the same way carrying_crystal already is. A player's own client also applies its own speed_multiplier/jump_multiplier from this to its local movement physics, since movement itself is simulated client-side.
- **player_teleport**: One reliable, targeted ReliableMsg::Teleport per teleport_player call, sent only to the named player_id, same targeted pattern as item_grants -- the host applies its own teleport locally instead of round-tripping through the network. A joined client's own interact-key press is reported the other direction, host-ward, as a reliable ReliableMsg::Interact carrying only the target position; the host reads the block there itself (its world state is authoritative) rather than trusting anything the client says about it.

## Persistence

- Saved fields: name, prompt, source, enabled
- Save format: Current saves use a VOXEL_SAVE_2 header followed by JSON, with modules in world.modules. The loader also accepts legacy bincode WorldSave files. Preserve legacy decoding when changing saved structures.

A module's Lua runtime state (persistent global tables/variables used to remember things between calls, e.g. a "previous tick" table keyed by player id) is NOT saved. Reloading a world re-executes `source` from scratch in a fresh Lua VM, so any such memory resets to its initial value -- only a module's enabled/disabled flag and source code survive a save/reload, never its accumulated runtime state.

Whether a module is a RULE or an INSTANT SPELL is NOT a saved field -- like api_version_tagging below, it's derived every load by re-executing `source` and checking which of on_tick/on_cast it defines (Module::is_instant). This is deliberate, following the same ModuleSaveEntry-stays-frozen discipline api_version_tagging established: it keeps the two kinds fully interchangeable in the save format and means older saved modules remain compatible.

Host health, poison, movement multipliers and oxygen are saved in current saves; legacy saves without PlayerSave use starting values. Guest transient vitals reset on reconnect. Resource inventories are saved in host/guest crafting accounts and restored on reload. Optional campkeeper contract progress, recovery count and recovery location are saved with each crafting account. Old accounts default to the first contract. Defeated players recover after three seconds at a safe location near their camp, retaining inventory, restoring health/oxygen and clearing poison and movement multipliers. Recovery grants ten seconds of protection from creature attacks. Campkeepers are stationary visual inhabitants derived from campfire blocks, not creatures addressable by creature IDs.

Every module's `source` may begin with a `-- api_version: X.Y.Z` comment line recording which World API version it was written/generated against. Rules generated by the LLM pipeline always get this tag added automatically; hand-written starter rules under modules/ carry it too. It is informational only (never enforced/validated against the running engine's version) so that older untagged rules keep loading exactly as before -- see CHANGELOG.md.

## Budgets and limits

### `native_work_per_invocation` = 65536
- Scope: per callback; conservative logical query/action work, not CPU instructions
- Applies to: `all_methods`
- On exhausted: Uncatchable budget failure with callback rollback.

### `creatures_max` = 256
- Scope: live creatures, including starter creatures; enforced on World API spawns
- Applies to: `spawn_creature`, `spawn_creature_near_player`
- On exhausted: Returns nil without reserving an ID; destroy a creature to free capacity.

### `api_calls_per_invocation` = 512
- Scope: per module callback, shared by all API methods, including failed calls
- Applies to: `all_methods`
- On exhausted: Uncatchable budget failure; continuous rule disabled, instant cast fails.

### `broadcasts_per_invocation` = 8
- Scope: per module callback
- Applies to: `broadcast`
- On exhausted: Uncatchable budget failure.

### `broadcast_bytes_max` = 512
- Scope: UTF-8 bytes per message
- Applies to: `broadcast`
- On exceeded: Uncatchable budget failure; message is not queued or logged.

### `coordinate_abs_max` = 1000000
- Scope: absolute value of any explicit API x/y/z coordinate, in blocks
- Applies to: `nearest_player`, `get_block`, `replace_block`, `terrain_height`, `distance`, `find_creatures`, `nearest_creature`, `find_blocks`, `chase`, `spawn_creature`, `teleport_player`
- On exceeded: Argument error before native execution. All numeric arguments, including numeric strings, must also be finite and representable as f32.

### `block_edits_per_call` = 32
- Scope: per module, per on_tick/on_death/on_block_break call
- Applies to: `replace_block`
- On exhausted: replace_block returns false; not an error.

### `creature_spawns_per_call` = 4
- Scope: per module, per call
- Applies to: `spawn_creature`, `spawn_creature_near_player`
- On exhausted: the call returns nil; not an error.

### `find_radius_max` = 10.0
- Scope: global
- Applies to: `find_creatures`, `find_blocks`, `spawn_creature_near_player`
- Note: find_creatures/find_blocks clamp their radius argument into [0, 10]; spawn_creature_near_player clamps into [1, 10] (its floor is 1, not 0). nearest_creature/nearest_player take no radius at all -- they search every creature/player unconditionally and return the closest.

### `find_results_max` = 64
- Scope: global
- Applies to: `find_creatures`, `find_blocks`
- On exceeded: results beyond the cap are silently dropped, not an error; don't rely on finding more than this.

### `block_edits_per_cast_call` = 300
- Scope: per instant-spell module, per on_cast call -- higher than block_edits_per_call since a spell runs once, not ~10/sec
- Applies to: `replace_block`
- On exhausted: replace_block returns false; not an error.

### `creature_spawns_per_cast_call` = 30
- Scope: per instant-spell module, per on_cast call -- higher than creature_spawns_per_call since a spell runs once, not ~10/sec
- Applies to: `spawn_creature`, `spawn_creature_near_player`
- On exhausted: the call returns nil; not an error.

### `item_grant_max` = 500
- Scope: per give_item call -- caps the amount argument itself, not a call count
- Applies to: `give_item`
- On exceeded: amount is silently clamped to this value, not an error.

### `attribute_multiplier_min` = 0.1
- Scope: global
- Applies to: `set_player_speed`, `set_player_jump`
- Note: A multiplier below this (e.g. 0) would functionally freeze/disable the attribute; clamped instead of allowed.

### `attribute_multiplier_max` = 5.0
- Scope: global
- Applies to: `set_player_speed`, `set_player_jump`
- On exceeded: multiplier is silently clamped into [attribute_multiplier_min, attribute_multiplier_max], not an error.

### `max_health` = 100.0
- Scope: every player, fixed -- not per-kind like a creature's max_health
- Applies to: `heal_player`
- Note: Also the starting health for every player, every session (see persistence.player_state_not_saved).

### `poison_tick_secs` = 10.0
- Scope: global -- how often every currently-poisoned player loses health, engine-driven, not a Lua call
- Applies to: `set_poisoned`
- Note: 1 health lost per tick, for as long as PlayerSnapshot.poisoned stays true. No Lua callback fires for this -- it's pure engine state, only observable by polling api.players()/nearest_player().health from on_tick.

### `oxygen_drain_per_sec` = 2.0
- Scope: global -- how fast PlayerSnapshot.oxygen falls while a player stands in a water block, engine-driven, not a Lua call
- Applies to: 
- Note: Full drain (100 -> 0) takes 50 seconds. No Lua callback fires for this either -- same purely-observable-by-polling story as poison_tick_secs.

### `oxygen_regen_per_sec` = 12.5
- Scope: global -- how fast PlayerSnapshot.oxygen recovers while a player is NOT submerged
- Applies to: 
- Note: Full recovery (0 -> 100) takes 8 seconds -- deliberately much faster than the drain, so surfacing reads as a real relief rather than a slow trickle back.

### `drowning_damage_per_sec` = 0.1
- Scope: global -- health lost per second once a player's oxygen has hit 0 and stayed there, for as long as they remain submerged
- Applies to: 
- Note: 1 health every 10 seconds -- slow enough to give a player time to notice and surface rather than punishing a moment of carelessness, but a real, escalating cost for staying under with no air. Stacks with poison_tick_secs if a player is unlucky enough to be both.

## Properties (`api.<name>`, read-only)

### `api.instant_mana_cost`: integer
- Engine cost per successful instant cast: normally 5, or 0 with host mana-free testing enabled. Reserved before on_cast and refunded on failure. Do not charge again in Lua.

### `api.rule_mana_cost`: integer
- Engine cost for successful generated rule creation: normally 20, or 0 with host mana-free testing enabled. Charged once to its author, no ongoing upkeep.

### `api.mana_regen_cap`: integer
- Passive recovery cap: 100. Connected players gain 1 mana every 5 seconds. Explicit grants/conversion may exceed the cap.

### `api.is_raining`: boolean
- True in rain or storm; refreshes after set_weather within a callback.

### `api.campfire_light_radius`: number
- Campfire maximum illumination radius: 8 blocks.

### `api.fish_spawn_clearance`: integer
- Required water cells beyond the fish center in each horizontal direction: 3 (a full 7x7 layer plus body clearance).

### `api.time_of_day`: number
- Range: [0, 1)
- 0 = sunrise, 0.25 = noon, 0.5 = sunset, 0.75 = midnight.

### `api.is_night`: boolean
- True once the sun is below the horizon (matches the point the sky finishes fading to full night).

### `api.weather`: string
- One of: sunny, rain, mist, storm, windy
- Current weather. sunny is the baseline (weighted heaviest when the engine picks the next weather on its own timer -- see set_weather). storm and windy both increase grass/leaf wind-sway noticeably (storm the most); mist reduces it and hazes the fog color. Only rain and storm render falling rain. "clear" is still accepted by set_weather as an alias for "sunny" (see set_weather), but this property itself only ever reports the current name, "sunny".

### `api.spawn_creature(kind, x, y, z)`
Spawns a new creature at a position. sheep/chicken/cow are passive by default; set_aggressive or attack can enable combat. stone_golem, wolf, stinger, goblin, sunscorch, zombie, skeleton, dragon_green, and dragon_red are different: all nine hostile entirely on their own, with no Lua involved -- each closes on and periodically damages the nearest player within its own aggro radius. stone_golem is large, slow, and hits hardest on the longest cooldown; sunscorch is a rare, tanky ghost that never gives up a chase and (like stone_golem) never speeds up while chasing -- no run animation, mechanically identical pace whether wandering or aggroed; goblin is a mid-weight melee bruiser (moderate speed/damage/cooldown, tankier than wolf); wolf is faster and lighter; stinger is fastest to attack (shortest cooldown) but hits lightest and is the most fragile. Zombies and skeletons only walk, including while chasing, and use melee attacks. Dragons are giant solitary predators: they walk, take off, fly and attack in either mode, and land again. Dragon homes must be at least 320 blocks apart across both colors; spawn returns nil inside another dragon territory, including earlier spawns in the same callback. Dragons stay within 64 blocks of home even during scripted chases. Fish are passive swimmers: they require a full 7x7 horizontal water area centered on the spawn position (three water blocks in each horizontal direction), including water around their whole body. Fish spawns in smaller pools or on land return nil. Fish only swim through connected water and occasionally jump straight up and return to the same water column. Fish never attack, even if aggression is enabled. Only spawn a hostile one when a hostile/dangerous creature is actually what the request wants.

Parameters:
  - `kind` (string) -- "sheep", "chicken", "stone_golem", "wolf", "stinger", "cow", "goblin", or "sunscorch", "zombie", "skeleton", "dragon_green", "dragon_red", "fish"; anything else (including a typo) silently becomes "sheep" -- not an error.
  - `x` (number)
  - `y` (number)
  - `z` (number)

Returns: `integer | nil` -- The new creature's id, or nil if this call's spawn budget is already used up or a dragon would violate territory spacing, or a fish lacks sufficient water.
Budget: see `creature_spawns_per_call` above.

### `api.spawn_creature_near_player(player_id, kind, radius)`
Spawns a new creature at a random point within radius blocks of a player (horizontally; height snaps to terrain). For fish, searches nearby loaded water instead, requiring the same pool-size check as spawn_creature; returns nil if no suitable pool is found. Prefer this over spawn_creature plus your own random offset when the rule is about spawning near a specific player.

Parameters:
  - `player_id` (integer)
  - `kind` (string) -- Same kinds as spawn_creature, including zombie, skeleton, dragon_green and dragon_red. Use these exact singular identifiers, not model variant filenames, plurals or dragon. Unknown strings silently spawn sheep.
  - `radius` (number) -- Clamped into [1, find_radius_max] -- note the floor is 1, not 0, unlike the find_* methods.

Returns: `integer | nil` -- The new creature's id, or nil for a missing player, exhausted spawn budget, creature population cap, insufficient fish habitat, or dragon territory overlap. Both dragon colors share a 320-block minimum home spacing, including spawns staged in this callback; nearby dragon packs cannot be spawned. Check for nil before using the id.
Budget: see `creature_spawns_per_call` above.

### `api.give_item(player_id, kind, amount)`

Budget: see `item_grant_max` above.

## Events

### `function on_tick(api)`
- Required: yes
- Frequency: ~10/sec, every tick_interval_secs, for as long as the module is enabled
- Defines a RULE module. Required unless the module defines on_cast instead -- a module must define EXACTLY ONE of on_tick or on_cast, never both, never neither; Module::load rejects any other combination.

### `function on_cast(api, event)`
- Required: no
- Frequency: Exactly once, immediately, when the host clicks Run in the Rules panel -- never on a timer, never re-run automatically.
- `event` shape: `CastEvent` (see Types above)
- Defines an INSTANT SPELL module instead of a RULE: a one-time immediate action with no ongoing condition to check (e.g. "add 100 stone", "spawn a dozen chickens around me", "heal me"), as opposed to a RULE's continuous "when/if/at night/while ..." behavior. Mutually exclusive with on_tick -- see on_tick's desc. Since it only runs once per click instead of ~10/sec, its per-call action budgets are higher than a RULE's -- see block_edits_per_cast_call and creature_spawns_per_cast_call.

### `function on_death(api, event)`
- Required: no
- `event` shape: `DeathEvent` (see Types above)
- Fires once per creature death, from any cause (this module's or another enabled module's api.damage/api.destroy). Does NOT chain: if an on_death handler itself kills another creature, that second death does not fire on_death again within the same tick.

### `function on_block_break(api, event)`
- Required: no
- `event` shape: `BlockBreakEvent` (see Types above)
- Fires once per real player-caused block break (mining). A rule's own replace_block calls, even ones that set a block to air, never trigger this.

### `function on_interact(api, event)`
- Required: no
- `event` shape: `InteractEvent` (see Types above)
- Fires once per real player-caused interact-key press (F) aimed at a block, whether or not anything is actually done in response -- the non-destructive counterpart to on_block_break, for a rule that reacts to a player deliberately using/examining something (e.g. a crystal that heals on touch) rather than mining it. Never fires from a rule's own replace_block calls, and never changes the block itself.
