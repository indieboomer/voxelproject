# World API (v1.20.0)

> Generated by `tools/gen_world_api.py` from `world_api/schema.yaml` -- do not edit by hand.

The Lua API exposed to sandboxed rule modules as the `api` table passed into on_tick/on_cast/on_death/on_block_break/on_interact. Every member is flat under `api` (single "world" namespace) -- there is no api.player.*/api.world.* nesting yet. `namespace: world` is still tagged on each entry so a future namespace can be introduced without reshaping this schema or its generated artifacts.

## Sandbox / engine

- Runtime: Lua 5.4 via mlua
- Tick interval: 0.1s (~10/sec)
- Allowed stdlib: table, string, math
- Removed stdlib: os, io, require, debug, package (never exist in this sandbox)
- Memory limit: 8,388,608 bytes
- Time budget: 5ms per call (checked every 1000 instructions)
- Instruction limit: 100,000 per initialization/callback
- Source limit: 65,536 UTF-8 bytes

Source is limited to 65,536 UTF-8 bytes. Initialization and every callback each receive 100,000 Lua instructions and a 5ms wall-time budget. Hooks check every 1,000 instructions; API entry/exit and execution completion also check time. Limits reset for each invocation. Budget exhaustion cannot be caught or suppressed with pcall/xpcall; ordinary Lua errors remain catchable. Native operations are not forcibly interrupted, so the time budget is a cooperative limit, not a hard realtime deadline. Each host tick/cast dispatch admits at most 16 callbacks under shared ceilings of 400,000 instructions, 4,096 API calls, 262,144 native work units and 20ms cooperative time. Admission reserves the full per-callback allowance (plus initialization for a failed VM reload); unstarted work waits for a later dispatch without resetting or replaying the callback. Environment queries/actions charge 200 units times (1 + staged block edits); find_campfires charges twice its bounding cube times (1 + staged block edits). Creature snapshots also account for staged-block lookups for in_water. Native work is limited to 65,536 units per callback: find_blocks charges its bounding cube candidates times (1 + staged block edits); other methods charge 1 + creature count + player count + staged player effects + staged block edits. find_blocks also checks time between scan rows. These units conservatively bound repeated scans, not CPU instructions or hard realtime.

Pending callbacks use round-robin recipient queues, FIFO within each rule. Tick requests coalesce to one pending tick per rule. Events retain their original recipient and payload, but query current world state when run. Disabling/deleting a rule cancels its queued work. Re-enabling a rule or adding a new rule never delivers old events to that new activation. Queues hold at most 512 callbacks total and 64 per module; newest excess requests are dropped with a visible saturation notice. Only the first 512 incoming block-break events and first 512 interactions per dispatch are considered. Queues are transient and are not saved on world exit. Up to 64 modules are loaded; saved overflow or invalid source is preserved without execution and reported to the host. Removing loaded modules and reloading the world can make room for preserved overflow modules.

Each module gets its own Lua VM: one module's globals/persistent state can never leak into another's. Initialization errors reject the module; an unhandled callback error or instruction/time/API-call/broadcast budget violation disables a continuous rule and notifies the host. An instant spell reports failure for that cast and can be run again. Lua memory allocations are capped at 8 MiB; ordinary Lua errors, including allocation errors, can be handled by pcall/xpcall. World effects are staged per callback and committed only after successful execution and final budget checks. Failed callbacks discard every staged effect. Before retrying a failed cast or reactivating a failed rule, its Lua VM is rebuilt from source; Lua globals reset because explicit persistent module state is not implemented yet.

## Callback transactions

Each callback is one transaction. Block edits, creature spawning/chasing/ damage/destruction, player effects, inventory changes, weather (including its RNG/timer), time, and broadcasts are staged. Queries read the callback's own accepted writes plus earlier successful callbacks in the same host dispatch. Returned query tables are snapshots; query again after an action. time_of_day/is_night/weather properties refresh after API calls. Movement and physics are not simulated during a callback; terrain_height remains the procedural generator height, not a scan of edited blocks. Failed callbacks emit no death events, broadcasts, replication effects, or spawn ID/RNG advances. Successful callbacks commit in scheduler order. Death events enqueue one level of notifications only after their cause commits. A failing death handler rolls back only its own changes, not the earlier death that triggered it. Ordinary errors caught by Lua do not abort the transaction; instruction/time/API/native-work/broadcast budget failures cannot be caught. This is callback failure rollback, not user-facing history/undo or atomic network delivery. Shared admission bounds callback work; native commit/apply and operating-system scheduling can overrun the cooperative wall-time target.

## Multiplayer authority

Every World API call executes ONLY on the host -- Lua does not run on joined clients at all (ScriptHost is host-only state). A module's effects (block edits, creature spawns/state, weather, time of day, broadcasts, item grants, player attributes, player teleports) reach clients purely through the replication channels below; there is no separate "multiplayer mode" a rule opts into. Only the host can generate, activate, or run a module (a menu/UI restriction, not something this API itself enforces or exposes) -- so an on_cast's `event.player_id` is currently always the host's own id, even though the API shape allows for any player.

Replication channel per kind of effect:

- **block_edits**: Retried until acknowledged and deduplicated (ReliableMsg::BlockEdit), but NOT ordered. Reordered writes to the same block can leave a client stale; ordered/revisioned replication is pending.
- **creature_state**: Best-effort, ~20 Hz (UnreliableMsg::Snapshot) -- a dropped snapshot is superseded by the next; no guaranteed delivery, but self-healing within one snapshot interval.
- **weather_and_time_of_day**: Carried in the same best-effort Snapshot as creature state -- see creature_state.
- **broadcast_messages**: One reliable Notify message per api.broadcast call, the same path used for host system notifications (rule enabled/disabled, player joined, etc.).
- **item_grants**: The host owns inventories for all players. Guest give_item/take_item changes are sent through reliable targeted CraftState updates; the host applies its own changes locally.
- **player_attributes**: health, poisoned, speed_multiplier, jump_multiplier, and oxygen all ride the same best-effort Snapshot creature_state already uses (~20Hz, self-healing) -- broadcast to every connected player, not just the one they belong to, the same way carrying_crystal already is. A player's own client also applies its own speed_multiplier/jump_multiplier from this to its local movement physics, since movement itself is simulated client-side.
- **player_teleport**: One reliable, targeted ReliableMsg::Teleport per teleport_player call, sent only to the named player_id, same targeted pattern as item_grants -- the host applies its own teleport locally instead of round-tripping through the network. A joined client's own interact-key press is reported the other direction, host-ward, as a reliable ReliableMsg::Interact carrying only the target position; the host reads the block there itself (its world state is authoritative) rather than trusting anything the client says about it.

## Persistence

- Saved fields: name, prompt, source, enabled
- Save format: bincode, inside WorldSave.modules (see save.rs) -- ModuleSaveEntry's field set is part of the save file's binary layout, so it cannot gain/lose/reorder fields without breaking old saves; see the changelog for how to evolve it safely.

A module's Lua runtime state (persistent global tables/variables used to remember things between calls, e.g. a "previous tick" table keyed by player id) is NOT saved. Reloading a world re-executes `source` from scratch in a fresh Lua VM, so any such memory resets to its initial value -- only a module's enabled/disabled flag and source code survive a save/reload, never its accumulated runtime state.

Every module's `source` may begin with a `-- api_version: X.Y.Z` comment line recording which World API version it was written/generated against. Rules generated by the LLM pipeline always get this tag added automatically; hand-written starter rules under modules/ carry it too. It is informational only (never enforced/validated against the running engine's version) so that older untagged rules keep loading exactly as before -- see CHANGELOG.md.

## Budgets and limits

### `native_work_per_invocation` = 65536
- Scope: per callback; conservative logical query/action work, not CPU instructions
- Applies to: `all_methods`
- On exhausted: Uncatchable budget failure with callback rollback.

### `creatures_max` = 256
- Scope: live creatures, including starter creatures; enforced on World API spawns
- Applies to: `spawn_creature`, `spawn_creature_near_player`
- On exhausted: Returns nil without reserving an ID; destroy a creature to free capacity.

### `api_calls_per_invocation` = 512
- Scope: per module callback, shared by all API methods, including failed calls
- Applies to: `all_methods`
- On exhausted: Uncatchable budget failure; continuous rule disabled, instant cast fails.

### `broadcasts_per_invocation` = 8
- Scope: per module callback
- Applies to: `broadcast`
- On exhausted: Uncatchable budget failure.

### `broadcast_bytes_max` = 512
- Scope: UTF-8 bytes per message
- Applies to: `broadcast`
- On exceeded: Uncatchable budget failure; message is not queued or logged.

### `coordinate_abs_max` = 1000000
- Scope: absolute value of any explicit API x/y/z coordinate, in blocks
- Applies to: `nearest_player`, `get_block`, `replace_block`, `terrain_height`, `distance`, `find_creatures`, `nearest_creature`, `find_blocks`, `chase`, `spawn_creature`, `teleport_player`
- On exceeded: Argument error before native execution. All numeric arguments, including numeric strings, must also be finite and representable as f32.

### `block_edits_per_call` = 32
- Scope: per module, per on_tick/on_death/on_block_break call
- Applies to: `replace_block`
- On exhausted: replace_block returns false; not an error.

### `creature_spawns_per_call` = 4
- Scope: per module, per call
- Applies to: `spawn_creature`, `spawn_creature_near_player`
- On exhausted: the call returns nil; not an error.

### `find_radius_max` = 10.0
- Scope: global
- Applies to: `find_creatures`, `find_blocks`, `spawn_creature_near_player`
- Note: find_creatures/find_blocks clamp their radius argument into [0, 10]; spawn_creature_near_player clamps into [1, 10] (its floor is 1, not 0). nearest_creature/nearest_player take no radius at all -- they search every creature/player unconditionally and return the closest.

### `find_results_max` = 64
- Scope: global
- Applies to: `find_creatures`, `find_blocks`
- On exceeded: results beyond the cap are silently dropped, not an error; don't rely on finding more than this.

### `block_edits_per_cast_call` = 300
- Scope: per instant-spell module, per on_cast call -- higher than block_edits_per_call since a spell runs once, not ~10/sec
- Applies to: `replace_block`
- On exhausted: replace_block returns false; not an error.

### `creature_spawns_per_cast_call` = 30
- Scope: per instant-spell module, per on_cast call -- higher than creature_spawns_per_call since a spell runs once, not ~10/sec
- Applies to: `spawn_creature`, `spawn_creature_near_player`
- On exhausted: the call returns nil; not an error.

### `item_grant_max` = 500
- Scope: per give_item call -- caps the amount argument itself, not a call count
- Applies to: `give_item`
- On exceeded: amount is silently clamped to this value, not an error.

### `attribute_multiplier_min` = 0.1
- Scope: global
- Applies to: `set_player_speed`, `set_player_jump`
- Note: A multiplier below this (e.g. 0) would functionally freeze/disable the attribute; clamped instead of allowed.

### `attribute_multiplier_max` = 5.0
- Scope: global
- Applies to: `set_player_speed`, `set_player_jump`
- On exceeded: multiplier is silently clamped into [attribute_multiplier_min, attribute_multiplier_max], not an error.

### `max_health` = 100.0
- Scope: every player, fixed -- not per-kind like a creature's max_health
- Applies to: `heal_player`
- Note: Also the starting health for every player, every session (see persistence.player_state_not_saved).

### `poison_tick_secs` = 10.0
- Scope: global -- how often every currently-poisoned player loses health, engine-driven, not a Lua call
- Applies to: `set_poisoned`
- Note: 1 health lost per tick, for as long as PlayerSnapshot.poisoned stays true. No Lua callback fires for this -- it's pure engine state, only observable by polling api.players()/nearest_player().health from on_tick.

### `oxygen_drain_per_sec` = 2.0
- Scope: global -- how fast PlayerSnapshot.oxygen falls while a player stands in a water block, engine-driven, not a Lua call
- Applies to: 
- Note: Full drain (100 -> 0) takes 50 seconds. No Lua callback fires for this either -- same purely-observable-by-polling story as poison_tick_secs.

### `oxygen_regen_per_sec` = 12.5
- Scope: global -- how fast PlayerSnapshot.oxygen recovers while a player is NOT submerged
- Applies to: 
- Note: Full recovery (0 -> 100) takes 8 seconds -- deliberately much faster than the drain, so surfacing reads as a real relief rather than a slow trickle back.

### `drowning_damage_per_sec` = 0.1
- Scope: global -- health lost per second once a player's oxygen has hit 0 and stayed there, for as long as they remain submerged
- Applies to: 
- Note: 1 health every 10 seconds -- slow enough to give a player time to notice and surface rather than punishing a moment of carelessness, but a real, escalating cost for staying under with no air. Stacks with poison_tick_secs if a player is unlucky enough to be both.

## Types

### `PlayerSnapshot`
One connected player's state, as returned by players()/nearest_player().

  - `id` (integer) -- Stable per-connection player id; 0 is always the host.
  - `x` (number)
  - `y` (number)
  - `z` (number)
  - `carrying_crystal` (boolean) -- True once this player has ever broken a Crystal block this session. One-shot: never resets to false from this API (there is no 'drop crystal' action).
  - `speed` (number) -- Horizontal speed in blocks/sec -- excludes vertical (fall/jump) motion.
  - `vertical_speed` (number) -- Signed vertical speed: positive while rising (e.g. jumping), negative while falling.
  - `on_ground` (boolean) -- True when standing on solid ground. Never true the same tick vertical_speed is positive -- a jump sets both at once, so 'on_ground and vertical_speed > 0' can never be true. There is no separate on_jump/on_land event; detect a one-shot transition by remembering the previous tick's on_ground per player id.
  - `running` (boolean) -- True while sprinting, as opposed to walking.
  - `in_water` (boolean) -- True while standing in a water block.
  - `health` (number) -- 0-100. Starts at 100 for every player every session -- like resources, health is NOT saved/reloaded with the world (see persistence.player_state_not_saved).
  - `poisoned` (boolean) -- While true, this player loses 1 health every poison_tick_secs, until something sets it back to false (e.g. a future medication item -- see set_poisoned). Sourced from and reported through this flag only; there is no separate 'poison timer' exposed.
  - `speed_multiplier` (number) -- Multiplies this player's base walk/sprint speed. 1.0 = normal; see set_player_speed.
  - `jump_multiplier` (number) -- Multiplies this player's base jump speed (so roughly jump *height* scales with its square, not linearly). 1.0 = normal; see set_player_jump.
  - `oxygen` (number) -- 0-100. Drains by oxygen_drain_per_sec while this player is standing in a water block, regenerates by oxygen_regen_per_sec otherwise, capping at 100 when not submerged. Once it reaches 0 and stays there, health starts draining too (drowning_damage_per_sec) -- pure engine state, purely a function of being in water; there is no api.set_player_oxygen, nothing else moves this value.

  - `flow_speed` (number) -- Visual animation speed: 1.4 when flowing, otherwise 0. No movement force.
  - `visual_only` (boolean) -- Always true.

Passed as `event` to on_cast.

### `DeathEvent`
Passed as `event` to on_death. The creature no longer exists by the time this fires.

  - `x` (integer)

Passed as `event` to on_interact. Fires on a deliberate, non-destructive 'use' aimed at a block (the E key), never changes the block itself -- same shape as BlockBreakEvent, but the block still exists afterward.

  - `x` (integer)
  - `y` (integer)
  - `z` (integer)
  - `player_id` (integer) -- id of the player who interacted (matches PlayerSnapshot.id).

## Properties (`api.<name>`, read-only)

### `api.is_raining`: boolean
- True in rain or storm; refreshes after set_weather within a callback.

### `api.campfire_light_radius`: number
- Campfire maximum illumination radius: 8 blocks.

### `api.fish_spawn_clearance`: integer
- Required water cells beyond the fish center in each horizontal direction: 3 (a full 7x7 layer plus body clearance).

### `api.time_of_day`: number
- Range: [0, 1)
- 0 = sunrise, 0.25 = noon, 0.5 = sunset, 0.75 = midnight.

### `api.is_night`: boolean
- True once the sun is below the horizon (matches the point the sky finishes fading to full night).

### `api.weather`: string
- One of: sunny, rain, mist, storm, windy
- Current weather. sunny is the baseline (weighted heaviest when the engine picks the next weather on its own timer -- see set_weather). storm and windy both increase grass/leaf wind-sway noticeably (storm the most); mist reduces it and hazes the fog color. Only rain and storm render falling rain. "clear" is still accepted by set_weather as an alias for "sunny" (see set_weather), but this property itself only ever reports the current name, "sunny".

## Query methods (`api.<name>(...)`)

### `api.get_campfire(x, y, z)`
Inspect a campfire block, including burning and night-light state.

Parameters:
  - `x` (integer)
  - `y` (integer)
  - `z` (integer)

Returns: `CampfireSnapshot | nil` -- nil unless this block is a campfire.

### `api.find_campfires(x, y, z, radius)`
Find nearby campfire snapshots; respects callback scan budgets. Prefer small radii and avoid nested scans.

Parameters:
  - `x` (integer)
  - `y` (integer)
  - `z` (integer)
  - `radius` (number) -- Clamped to 0..12.

Returns: `CampfireSnapshot[]` -- At most find_results_max entries in scan order, not nearest order.

### `api.get_water(x, y, z)`
Inspect water depth, surface elevation, and the visual river/stream current. No fluid simulation or writable flow override.

Parameters:
  - `x` (integer)
  - `y` (integer)
  - `z` (integer)

Returns: `WaterSnapshot | nil` -- nil unless the queried block is water. Reads staged edits.

### `api.get_waterfalls(x, y, z)`
Inspect spills at a source water block. Requires open sky, an adjacent open drop, loaded neighbors, and lower receiving water. Use get_water().surface_y-1 to query its top block.

Parameters:
  - `x` (integer)
  - `y` (integer)
  - `z` (integer)

Returns: `WaterfallSnapshot[]` -- Zero to four directional spills. Changing source, receiving water, or obstructions through replace_block changes the effect; reads staged edits.

### `api.can_spawn_fish(x, y, z)`
Check a submerged fish body and full 7x7 water layer centered at floor(x,y,z). Reads staged edits.

Parameters:
  - `x` (number)
  - `y` (number)
  - `z` (number)

Returns: `boolean`

## Action methods (`api.<name>(...)`)

### `api.place_campfire(x, y, z)`
Place an indefinitely burning campfire on loaded grass, soil, sand, or stone with four air blocks above the support. Uses one shared block edit; no recipe or inventory cost.

Parameters:
  - `x` (integer)
  - `y` (integer)
  - `z` (integer)

Returns: `boolean` -- False for occupied, unsupported, unloaded, out-of-height, or exhausted-budget sites. To remove, replace_block(x,y,z,'air').

### `api.spawn_fish(x, y, z)`
Spawn a swimming fish only where can_spawn_fish succeeds. Reads staged water edits and shares the normal creature spawn budget, including failed attempts. Use chase(id,x,y,z) each tick to guide it within connected water.

Parameters:
  - `x` (number)
  - `y` (number)
  - `z` (number)

Returns: `integer | nil` -- Stable creature id, or nil when habitat is unsuitable or spawn/entity budget is exhausted.
Budget: see `creature_spawns_per_call` above.

### `api.chase(creature_id, x, y, z)`
Makes a creature move toward a point at increased speed, overriding explicit targeting and suppressing automatic attacks while the chase lease is active. Call it again every tick to keep it chasing -- stop calling it and the creature reverts to normal wandering within about a third of a second (use ignore to stop chasing).

Parameters:
  - `creature_id` (integer)
  - `x` (number)
  - `y` (number)
  - `z` (number)

Returns: `nil` -- Always nil, even if creature_id doesn't exist -- there is no way to tell from Lua whether the call actually found the creature.

### `api.protect_player(player_id, kind)`
On_tick only: prevent melee damage/attack animation from creature kind against this player without changing creature aggression or creature-to-creature combat. Rule-owned temporary policy: refresh every tick while condition holds; an empty next tick removes it. Disable/delete/error releases it; other rules' protections remain. Saved rules recompute policies after reload.

Parameters:
  - `player_id` (integer)
  - `kind` (string)

Returns: `boolean` -- False for unknown player/species, true otherwise.

### `api.suppress_creature_attacks(creature_id)`
On_tick only: temporarily prevent this creature's melee attacks against all targets. Same rule-owned cleanup as protect_player. Does not change underlying aggression, target or movement. Refresh only while the condition holds.

Parameters:
  - `creature_id` (integer)

Returns: `boolean` -- False for missing creature.

### `api.set_aggressive(creature_id, aggressive)`
Set automatic player aggression, cancel explicit targeting and restore normal wandering/automatic AI. False makes even hostile species peaceful. True lets passive species attack too (2 damage, 1.5 reach, 2 second cooldown, 16 block detection).

Parameters:
  - `creature_id` (integer)
  - `aggressive` (boolean)

Returns: `boolean` -- False for missing IDs or invalid targets.

Parameters:

  - `target_type` (string)
  - `target_id` (integer)

Returns: `boolean` -- False for missing IDs or invalid targets.

### `api.select_target(creature_id, kind, radius)`
Select nearest live target of kind player, sheep, chicken, cow, wolf, stone_golem, stinger, goblin, sunscorch, zombie, skeleton, dragon_green, dragon_red, or fish within radius (clamped to query limit). Excludes self. Returns target ID or nil; no match clears selection. Does not start an action; follow with attack or chase_target.

### `api.spawn_creature(kind, x, y, z)`
Spawns a new creature at a position. sheep/chicken/cow are passive by default; set_aggressive or attack can enable combat. stone_golem, wolf, stinger, goblin, sunscorch, zombie, skeleton, dragon_green, and dragon_red are different: all nine hostile entirely on their own, with no Lua involved -- each closes on and periodically damages the nearest player within its own aggro radius. stone_golem is large, slow, and hits hardest on the longest cooldown; sunscorch is a rare, tanky ghost that never gives up a chase and (like stone_golem) never speeds up while chasing -- no run animation, mechanically identical pace whether wandering or aggroed; goblin is a mid-weight melee bruiser (moderate speed/damage/cooldown, tankier than wolf); wolf is faster and lighter; stinger is fastest to attack (shortest cooldown) but hits lightest and is the most fragile. Zombies and skeletons only walk, including while chasing, and use melee attacks. Dragons are giant solitary predators: they walk, take off, fly and attack in either mode, and land again. Dragon homes must be at least 320 blocks apart across both colors; spawn returns nil inside another dragon territory, including earlier spawns in the same callback. Dragons stay within 64 blocks of home even during scripted chases. Fish are passive swimmers: they require a full 7x7 horizontal water area centered on the spawn position (three water blocks in each horizontal direction), including water around their whole body. Fish spawns in smaller pools or on land return nil. Fish only swim through connected water and occasionally jump straight up and return to the same water column. Fish never attack, even if aggression is enabled. Only spawn a hostile one when a hostile/dangerous creature is actually what the request wants.

Parameters:
  - `kind` (string) -- "sheep", "chicken", "stone_golem", "wolf", "stinger", "cow", "goblin", or "sunscorch", "zombie", "skeleton", "dragon_green", "dragon_red", "fish"; anything else (including a typo) silently becomes "sheep" -- not an error.
  - `x` (number)
  - `y` (number)
  - `z` (number)

Returns: `integer | nil` -- The new creature's id, or nil if this call's spawn budget is already used up or a dragon would violate territory spacing, or a fish lacks sufficient water.
Budget: see `creature_spawns_per_call` above.

### `api.spawn_creature_near_player(player_id, kind, radius)`
Spawns a new creature at a random point within radius blocks of a player (horizontally; height snaps to terrain). For fish, searches nearby loaded water instead, requiring the same pool-size check as spawn_creature; returns nil if no suitable pool is found. Prefer this over spawn_creature plus your own random offset when the rule is about spawning near a specific player.

Parameters:
  - `player_id` (integer)
  - `kind` (string) -- Same silent-default-to-sheep behavior as spawn_creature.
  - `radius` (number) -- Clamped into [1, find_radius_max] -- note the floor is 1, not 0, unlike the find_* methods.

Returns: `integer | nil` -- The new creature's id, or nil if player_id isn't connected OR the spawn budget is used up -- these two failure cases are indistinguishable from Lua.
Budget: see `creature_spawns_per_call` above.

## Events

### `function on_tick(api)`
- Required: yes
- Frequency: ~10/sec, every tick_interval_secs, for as long as the module is enabled
- Defines a RULE module. Required unless the module defines on_cast instead -- a module must define EXACTLY ONE of on_tick or on_cast, never both, never neither; Module::load rejects any other combination.

### `function on_cast(api, event)`
- Required: no
- Frequency: Exactly once, immediately, when the host clicks Run in the Rules panel -- never on a timer, never re-run automatically.
- `event` shape: `CastEvent` (see Types above)
- Defines an INSTANT SPELL module instead of a RULE: a one-time immediate action with no ongoing condition to check (e.g. "add 100 stone", "spawn a dozen chickens around me", "heal me"), as opposed to a RULE's continuous "when/if/at night/while ..." behavior. Mutually exclusive with on_tick -- see on_tick's desc. Since it only runs once per click instead of ~10/sec, its per-call action budgets are higher than a RULE's -- see block_edits_per_cast_call and creature_spawns_per_cast_call.

### `function on_death(api, event)`
- Required: no
- `event` shape: `DeathEvent` (see Types above)
- Fires once per creature death, from any cause (this module's or another enabled module's api.damage/api.destroy). Does NOT chain: if an on_death handler itself kills another creature, that second death does not fire on_death again within the same tick.

### `function on_block_break(api, event)`
- Required: no
- `event` shape: `BlockBreakEvent` (see Types above)
- Fires once per real player-caused block break (mining). A rule's own replace_block calls, even ones that set a block to air, never trigger this.

### `function on_interact(api, event)`
- Required: no
- `event` shape: `InteractEvent` (see Types above)
- Fires once per real player-caused interact-key press (E) aimed at a block, whether or not anything is actually done in response -- the non-destructive counterpart to on_block_break, for a rule that reacts to a player deliberately using/examining something (e.g. a crystal that heals on touch) rather than mining it. Never fires from a rule's own replace_block calls, and never changes the block itself.
